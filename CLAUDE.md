# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Loadstone for Windows is a tray-only WPF window tiler (.NET 10, WPF-UI, Win32 through `LibraryImport`). It tiles the focused window into halves, corners, and thirds from global hotkeys or by dragging a window to a screen edge. It is the Windows port of the macOS Loadstone at `C:\code\projects\loadstone`, which remains the authority on behavior: same command ids, same tile math, same drag zones, same one-shot Restore. Architecture: **Pure WPF** (see `docs/superpowers/specs/2026-09-07-loadstone-win-design.md`; that spec is the pre-implementation design kept as a record, and its "Drift from the shipped implementation" section lists where the code went another way). Cite spec sections by number *and* heading name — the numbers drift when a section is inserted, the headings do not.

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -File tools/icons/generate.ps1   # regenerate the .ico assets
& 'C:\Program Files\PowerShell\7\pwsh.exe' -File scripts/version-manager.ps1 show   # the one version
& 'C:\Program Files\PowerShell\7\pwsh.exe' -File build/build-msix.ps1              # build the Store package
& 'C:\Program Files\PowerShell\7\pwsh.exe' -File build/build-installer.ps1            # build the beta installer (needs Inno Setup 6.3+)
```

`global.json` opts the repo into the Microsoft.Testing.Platform runner (xunit.v3), so a positional `dotnet test Loadstone.slnx` and `--logger` do not apply; use `--solution`/`--project` and `--report-trx`. Filtering does work: `--filter` still takes VSTest syntax (`--filter "FullyQualifiedName~Win32Window"`), and xunit.v3 adds simple filters `--filter-class`, `--filter-method`, `--filter-namespace`, `--filter-trait` and their `--filter-not-*` variants. Pick one family per run: `--filter` cannot be combined with `--filter-query` or the simple filters.

The 32-bit `pwsh` is first on PATH on the development machine; scripts that touch Win32 must run under the 64-bit one above. Real-window tests run under `[WpfFact]` and need a desktop session. The first windows-latest run passed with 287 tests and 0 skipped, so the hosted runner does create real windows and no environment gate is needed today. Keep the option for the day a runner image changes, but note it would have to cover more than `TestWindow`: `HotkeyRegistrarTests`, the UI `SmokeTests`, `KeyboardLayoutProbeTests`, `SystemParametersNativeSnapSettingsTests`, and `SettingsWindowTests` all need a real session too. `build/build-installer.ps1` additionally needs Inno Setup 6.3 or newer (`winget install --id JRSoftware.InnoSetup`); winget installs it per-user under `%LOCALAPPDATA%\Programs\Inno Setup 6` and puts nothing on PATH, which is why the script probes that location before Program Files. On a GitHub `windows-latest` runner `iscc` is already on PATH.

Reading the app's log: `%LOCALAPPDATA%\Loadstone\Logs\Loadstone-<date>.log`. Settings: `%LOCALAPPDATA%\Loadstone\settings.json`. Both paths hold whether the app is run with `dotnet run` or launched from an installed package — MSIX does not redirect file-system writes for this package configuration, only the registry (see the MSIX spike results below, question 3).

## Architecture

Data flows one direction: input → `CommandDispatcher` / `DragSnapMonitor` → `WindowDirector` → `Win32Window` → `SetWindowPos`.

- **Core (`src/Loadstone.Core`)** has no Win32 and no WPF. `Tile.Frame` floors the left and top pieces and gives the remainder to the right and bottom ones so complementary tiles meet on odd sizes. `SnapZones` maps the cursor against the *full* monitor frame (tiles are laid into the *work area*) and scales the 16 px bands and 140 px corners with the display's DPI. `ScreenGeometry.Neighbor` walks displays in reading order (x, then y). `WindowDirector` keeps the restore ledger: written only after a window accepts a frame, one-shot Restore, dead identities pruned before every command. `DragSnapTracker` arms once the dragged window's origin changes with its size unchanged, disarms on a resize, and commits at the end unless the frame is back at its baseline (Escape). The one exception to "a size change is a resize": a size that is the old one carried through the ratio of the two displays' DPIs is Windows rescaling the window on `WM_DPICHANGED`, so the tracker re-baselines and stays armed. Comparing DPIs alone was not enough — a resize can carry the frame's centre across a boundary by itself, and that read a dragged edge as a rescale. `NativeSnap` captures Windows' edge-snapping flags once, parks them as a crash marker through `INativeSnapMarker` (`FileNativeSnapMarker` writes `native-snap-marker.json` beside settings.json), and restores them; recovery runs before capture. The flags themselves are `NativeSnapFlag` values read and written through `INativeSnapFlags`.
- **UI (`src/Loadstone.UI`)**. `Interop/` holds every Win32 declaration. `Win32Window` is the only type that knows about invisible borders: `ReadFrame()` is the DWM extended frame bounds (a method, not a property — it is two or three Win32 calls and the answer changes between reads), `SetFrame` restores a maximized or minimized window first, expands the target by the border insets, and writes once more when the frame lands off target after a DPI change. It does no DPI arithmetic itself — that lives in `Displays.Snapshot` (reads `GetDpiForMonitor` onto every `Display`), `Display.Scale` (divides by 96), `SnapZones` (scales its bands by that), and `TestSetup` (sets the process awareness context); do not go looking for it in `Win32Window`. `HotkeyRegistrar` uses `RegisterHotKey` on a message-only window; `HotkeyCenter` resolves the effective chord per command and records in-use and keyboard-layout warnings. `WinEventMoveSizeEvents` hooks `EVENT_SYSTEM_MOVESIZESTART`/`END`; `DragSnapMonitor` samples the cursor at 60 Hz during a drag and commits after the OS finishes the drop. `SnapPreview` asserts topmost from its own process on every show. `TrayController` captures the foreground window before the menu opens.

### Invariants worth knowing before editing

- `WindowCommand` is the single source of truth for hotkeys, the tray menu, and the Shortcuts tab. Its ids (`leftHalf` … `previousDisplay`) are settings keys and match the Mac app; never rename one. `WindowCommandTests` pins the list. The switches that carry that invariant have no discard arm on purpose: `Tile.Title()` and `Tile.Frame()` over `Tile`, and `WindowCommands.Id()`, `Section()`, `ToTile()`, and `DefaultShortcut()` over `WindowCommand`. CS8524 is suppressed so a new member fails the build until each of those covers it. Two switches over `WindowCommand` do *not* have that protection — `WindowCommands.Title()` ends in `_ => throw new ArgumentOutOfRangeException(...)` and `WindowDirector.Perform`'s command switch in `default: throw` — because both handle only the non-tile commands and the compiler cannot see that the tile ones were already dealt with. Those throws are reachable, so a new command is not finished when the build goes green: a new *tile* command is carried through both by `ToTile()`, but a new *non-tile* one satisfies `Id()`, `Section()`, `ToTile()` (its `=> null` arm) and `DefaultShortcut()`, compiles, and then throws the first time the tray menu is built or the command is pressed. `WindowCommandTests.Title_AnswersForEveryCommand_WithNoTwoAlike` is the net; add the command to both switches by hand.
- Coordinates are physical pixels, y down, everywhere. The app manifest declares Per-Monitor V2; the test host opts in through a module initializer.
- `SystemParametersInfo` for `SPI_SETDOCKMOVING` and `SPI_SETSNAPSIZING` takes the BOOL in `uiParam` with `pvParam` zero. Passing it in `pvParam` silently writes FALSE (found the hard way on 2026-09-07).
- A background process cannot make another process's window topmost, but can make its own window topmost once it exists. The preview relies on the second fact; never ask another process's window to change z-order.
- Test fixtures use 1201 by 901 and negative-origin displays on purpose; even sizes hide rounding bugs.
- The native-snap crash marker has its own store — `INativeSnapMarker`, implemented by `FileNativeSnapMarker` over `native-snap-marker.json` — and not a key in settings.json, precisely so that parking it no longer raises `ISettingsService.Changed` and no longer re-enters every subscriber. `AppSettings.NativeSnapPreviousValues` survives for migration only: nothing writes it, and `NativeSnap` reads it once and clears it. That clear is the one re-entrant write left, from inside the `Changed` handler that turned drag snapping on, once per upgraded profile — which is why `NativeSnap.OnSettingsChanged` is flip-detecting and any new handler that writes settings must be too. `Changed` fires after every `Update`, on the thread that called it, and `SettingsService` isolates subscribers so one that throws does not stop the rest.
- `RegistryStartupRegistration.EnableAsync()` writes the Run value *and* deletes `StartupApproved\Run\Loadstone`. That is the one write outside the Run key, and it is deliberate: without it Task Manager's disable outlives re-enabling from Settings. `InitializeAsync()` rewrites the Run value only when the path it holds is gone from disk, so a `dotnet run` build never steals an installed copy's login item.
- Every test that creates a window runs under `[WpfFact]`. Tests never touch the real Run key (they use keys under `Software\LoadstoneTests` and delete that parent when they leave it empty), the real settings file (temp directories), the production single-instance names (each test makes its own), or change the snap flags (they write back the value they read).
- `src/Loadstone.UI/Loadstone.UI.csproj` sets `AllowUnsafeBlocks` because `LibraryImport` source generation requires it (SYSLIB1062). Core does not and must not need it.
- `System.Windows.Rect`/`Point` clash with `Loadstone.Core.Geometry.Rect`/`Point`; files that import both alias the Core type (`using Rect = Loadstone.Core.Geometry.Rect;`), see `src/Loadstone.UI/Input/SnapPreview.cs`.
- Fixed-size windows (no `WS_THICKFRAME`) keep their size on a tile command and are centered on the target frame, overhanging it if larger (spec 5.2, "Win32Window").
- xUnit analyzers run as errors: blocking waits in tests take `TestContext.Current.CancellationToken` (xUnit1051).
- `IStartupRegistration` has two implementations chosen by `IPackageIdentity`; inside a package the HKCU Run write succeeds, reads back, and does nothing, so the wrong choice is invisible at run time.
- `OnStartup` must not be made async — the dispatcher does not pump until it returns; deferred work goes through `Dispatcher.BeginInvoke`.
- The snap flags are written session-scoped (`SPIF_SENDCHANGE` only) because MSIX uninstall runs no application code: it terminates the process without `OnExit` or `SessionEnding`, and no Loadstone will ever run again to put the flags back. `%LOCALAPPDATA%\Loadstone\` and the marker in it survive an uninstall — see the MSIX spike results below, question 3 — so marker survival was never what made a persisted write unsafe; the absence of a future run was. The Inno Setup channel's uninstaller *can* run application code and still deliberately does not restore them (Inno spec 6.3, "What is deliberately left behind"): doing it properly would mean a command-line surface on `Loadstone.exe` for the uninstaller to call. Signing out restores them, and both channels then behave identically — so this is a decision, not an oversight to be fixed.
- `AppSettings.DragSnappingEnabled` defaults to `false`, and turning it on is the user's consent to Loadstone changing a Windows setting.
- The version lives in four files kept in sync by `scripts/version-manager.ps1` and pinned by `VersionConsistencyTests`.
- `packaging/msix/AppxManifest.xml` carries the real Partner Center identity (`Identity/@Name` `MortenBrudvik.Loadstone`, `@Publisher` `CN=E6ED6F6D-88CB-42AC-BED3-B0FA24EC28DD`), set in commit 338be70. `build/build-msix.ps1` still warns when it finds `PLACEHOLDER` in the staged manifest and deliberately does not fail: that guard stays for any future rebuild that reintroduces one, and the local packaging and sideload path is meant to keep working with placeholders in place.
- `packaging/inno/Loadstone.iss` touches the HKCU Run value only through `dontcreatekey uninsdeletevalue`. `deletevalue` fires at *install* time and would silently switch off every tester's launch-at-login on every upgrade; `uninsdeletekeyifempty` would delete the shared `Run` key for any user with no other startup entries. `AppId` is the installer's identity: change it and the next Setup installs a second copy beside the first instead of upgrading it. `ArchitecturesAllowed=x64compatible` is the one directive with a real consequence: narrow it to `x64` and an arm64 tester running under emulation is silently excluded. `ArchitecturesInstallIn64BitMode=x64compatible` has almost no effect on this installer — this per-user install always resolves `{autopf}` to `{userpf}` regardless of bit mode, and the only two registry keys it touches — the `Run` key and the uninstall key it reads back — are plain `HKCU` and neither is WOW64-redirected (unlike `HKCU\Software\Classes`, which is) — but it is set to match the x64 payload and left alone; there is no dramatic consequence to changing it. `InnoScriptTests` pins all of this, plus the exe name and the `Run` value name against `RegistryStartupRegistration.ValueName`. The script takes its version on the ISCC command line, so the version still lives in four files. Pascal Script comments `{ }` do not nest — an Inno constant written out inside one ends the comment early and the compile fails with `'BEGIN' expected`.

### Spike results (2026-09-07, Windows 11 25H2 build 26200)

With `DockMoving` and `SnapSizing` off, a window dragged to the left edge, a corner, or the top edge is left where it was dropped; with them on it snaps to the half, the quarter, or maximizes. The Snap Layouts flyout could not be observed (off on that machine) and is documented in the README instead of managed.

### MSIX spike results (2026-09-08, Windows 11 25H2 build 26200)

- Question 1 (`windows.startupTask` with `Enabled="false"`, turned on via `RequestEnableAsync`, actually launches at logon): **still unmeasured** — the task was left disabled for this spike (`StartupTask.State` read `Disabled`, and nothing called `RequestEnableAsync`), and the check needs a sign-out/sign-in cycle that only a human at the keyboard can do. Say so plainly rather than letting the other three answers imply this one passed too.
- Question 2 (`RequestEnableAsync` from the WPF STA UI thread deadlocking, and whether it prompts): **partly measured** — `StartupTask.GetAsync`, called from the queued `Dispatcher.BeginInvoke` continuation in `InitializeStartupAsync`, returned without deadlocking. The manifest's `Enabled="false"` read back as `StartupTaskState.Disabled`, which `PackagedStartupRegistration.Map` turns into `StartupStatus.NotRegistered` — and decisively, the real HKCU Run key held a value that `RegistryStartupRegistration` would have reported as `StartupStatus.Enabled`, so the app reporting `NotRegistered` instead proves the package-identity probe selected the *packaged* implementation for this run, not the registry one. `RequestEnableAsync` itself was never called, since the task was left disabled (question 1), so whether it deadlocks or prompts is still unmeasured.
- Question 3 (where `settings.json`, `native-snap-marker.json`, and the logs land under `%LOCALAPPDATA%\Packages\<PFN>\LocalCache\Local\Loadstone\`, and whether they survive a package update): **measured, and the premise was wrong** — after registering the package with `Add-AppxPackage -Register` and running it, file-system writes were not redirected at all: the log landed at the real `%LOCALAPPDATA%\Loadstone\Logs\Loadstone-2026-09-09.log`, the same path an unpackaged run uses. Under `%LOCALAPPDATA%\Packages\<PFN>` there was no `LocalCache\Local` tree; the only artefacts were registry-virtualization ones — `Settings\settings.dat` and `SystemAppData\Helium\*.dat` — confirming that it is the *registry*, not the filesystem, that MSIX virtualizes for this package configuration. `settings.json`, `native-snap-marker.json`, and the logs all live at the literal `%LOCALAPPDATA%\Loadstone\` path regardless of how the app was launched; the update-survival question is moot once the location does not move.
- Question 4 (does `SPIF_SENDCHANGE` alone make `SPI_SETDOCKMOVING`/`SPI_SETSNAPSIZING` take effect for the session, and does it read back the way `NativeSnap.Suppress()` expects) was measured directly with a P/Invoke probe, no package involved: both flags started `True`; writing `False` with `fWinIni = SPIF_SENDCHANGE` only (no `SPIF_UPDATEINIFILE`), BOOL in `uiParam`, `pvParam` zero, returned success from `SystemParametersInfoW`, and an immediate read-back reported `False` for both — the exact write-then-verify `NativeSnap.Suppress()` performs would not log an error. Restoring the original `True` values the same SPIF_SENDCHANGE-only way also read back correctly. `HKCU\Control Panel\Desktop`'s `DockMoving` and `SnapSizing` registry values stayed at `1` throughout — before the write, right after it, and after the restore — so nothing was persisted to the profile; the effect is session-only, as `SPIF_SENDCHANGE` without `SPIF_UPDATEINIFILE` implies. A sign-out was not performed, so whether logon restores the OS defaults on its own is unverified, but nothing in the app is relying on that — `NativeSnap` restores the flags itself.
